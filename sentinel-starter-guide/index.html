Getting Started with Microsoft Sentinel

Step 1: Create & Plan Your Log Analytics Workspace

📍 Portal path: Go to portal.azure.com → Search "Log Analytics workspaces" → + Create

Enable Microsoft Sentinel on the Workspace

After creating the workspace, enable Microsoft Sentinel on it: portal.azure.com → Search "Microsoft Sentinel" → + Create → Select the workspace → Add. Once added, Sentinel is active and ready for the next steps.

⚠️ Note: Once Sentinel is deployed on a workspace, moving that workspace to another resource group or subscription is not supported.
  • 📖 Onboard Microsoft Sentinel
⚠️ Always create a dedicated security workspace. Even if you already have a Log Analytics workspace (e.g., for IT ops or application monitoring), create a new, separate workspace specifically for security. Sharing a workspace with non-security workloads creates issues with RBAC, data retention policies, cost attribution, and compliance. The security workspace will be the one onboarded to Sentinel.

A dedicated Log Analytics workspace is the foundation of Microsoft Sentinel. All security data ingestion, detection, and investigation happens in this workspace. Plan your workspace architecture before creating it. These decisions affect cost, access control, network performance, and compliance.

DecisionGuidance
Dedicated security workspaceAlways create an independent Log Analytics workspace for security. Do not share with IT ops, application monitoring, or other non-security workloads. This ensures clean RBAC boundaries, separate retention policies, and accurate cost attribution
Region (proximity to workloads)Create the workspace in a region closest to where the actual workloads you're monitoring are running. For example, if your Azure architecture is concentrated in West Europe or Germany West Central, place the workspace there. This reduces egress, bandwidth, and network costs by keeping log data close to its source
Data residencyWorkspace region determines where data is stored. This is important for compliance (GDPR, local regulations)
Resource GroupCreate or use a dedicated security resource group (e.g., rg-security-sentinel) for clean management
Workspace NameUse a clear naming convention (e.g., law-sentinel-prod-westeurope) to distinguish from non-security workspaces
Single vs. multiple workspacesMost organizations start with a single workspace. Use multiple only for data residency, RBAC boundaries, or multi-tenant scenarios
Roles & permissionsUse RBAC with least-privilege. Key roles: Sentinel Reader, Responder, Contributor. Use PIM for just-in-time access
Pricing TierUse Pay-As-You-Go to start. Switch to Commitment Tiers once daily ingestion volume is predictable (100 GB/day+)
RetentionFirst 90 days of interactive retention is free with Sentinel. Interactive retention can be extended up to 730 days (2 years) at standard Log Analytics prices. For long-term/compliance needs, use total retention (data lake tier), up to 12 years at lower cost. You can also set different retention periods per table.

💡 Review these early, before connecting data sources. UEBA, anomalies, and health monitoring should be running when data starts flowing so Sentinel can build behavioral baselines and collect health metrics from day one.
📍 Portal path: Go to security.microsoft.com → System → Settings → Microsoft Sentinel → SIEM workspaces → select the workspace → review the workspace setting sections.

After you open the workspace, the key settings are on the same workspace configuration pane. Review these settings before data onboarding.

Sync Microsoft Entra ID, add on-premises Active Directory if Defender for Identity is deployed, and connect all eligible data sources where possible.

Step 5: Content Hub: Your Solution Library

The Content Hub is Microsoft Sentinel's built-in marketplace. It's where you find, install, and manage solutions. These are pre-packaged bundles of security content built by Microsoft, partners, and the community. Think of it as an app store for your SIEM.

📍 Portal path: Defender Portal → Microsoft Sentinel → Content management → Content Hub
💡 Why Content Hub matters: Instead of building detections, dashboards, and automations from scratch, you install a solution and get a complete security package for a specific product, threat, or compliance scenario, ready to activate in minutes.

What is a Solution?

A solution is a package that can contain any combination of the following assets, all designed to work together for a specific use case:

Asset TypeWhat It IsExample
Data Connector The pipeline that ingests logs from a data source into your Sentinel workspace Microsoft Entra ID connector pulls sign-in and audit logs
Analytic Rules Scheduled or real-time KQL queries that detect threats and create incidents automatically "Brute force attack against Azure Portal" rule fires when multiple failed sign-ins are detected
Workbooks Interactive dashboards that visualize security data for monitoring and reporting Azure AD Sign-in workbook shows login trends, risky sign-ins, and MFA gaps
Playbooks Logic Apps-based automated response workflows triggered by incidents or alerts Auto-disable a compromised user account and notify the SOC via Teams
Hunting Queries Proactive KQL queries used by analysts to search for threats that haven't triggered an alert yet Hunt for unusual PowerShell execution patterns across endpoints
Watchlists Reference lists (CSV-based) of entities like VIP users, critical IPs, or service accounts, used to enrich or filter alerts VIP user watchlist to auto-escalate incidents involving executives
Parsers KQL functions that normalize raw log data into a consistent schema (often ASIM-based) Parser that normalizes firewall logs into the ASIM Network Session schema for cross-vendor queries
💡 Key concept: A single solution can contain all of these assets. For example, the Microsoft Entra ID solution includes a data connector, analytic rules, workbooks, hunting queries, and parsers, all in one install.

Step 6: Connect & Ingest Your Data

Installing a solution from Content Hub gives you the assets — but connectors still need to be configured and data sources authorized before logs actually flow. This step is where you turn installed solutions into live data pipelines.

⚠️ Collection is not detection. Before enabling connectors, decide what data your SOC actually needs for detection, investigation, and hunting. Not everything needs to be ingested into the same tier.
Plan Your Ingestion Tiers

Classify each data source to balance security coverage against cost:

CategoryWhat it isExamplesWhere to store
Primary security data Critical security value — real-time detection, scheduled alerts, behaviour analytics, correlation. Must be readily available. Authentication logs, EDR/antivirus logs, cloud audit trails, threat intelligence feeds, security alerts Analytics tier (90 days free, up to 2 years interactive)
Secondary security data Supplemental, often high-volume. Limited real-time value but essential for investigations. Access on-demand. Cloud storage access logs, NetFlow, TLS/SSL certificate logs, firewall logs, proxy logs, IoT logs Data lake tier (cost-effective long-term, up to 12 years)
Enable Connectors: 5-Point Checklist
📍 Portal path: Defender Portal → Microsoft Sentinel → Configuration → Data connectors → Open connector page → Connect

Before you flip the switch on each connector, run through these checks:

#CheckWhy
1 Free data source? Azure Activity, Office 365 audit logs, and Defender security alerts cost nothing to ingest. Enable these first. Full free list → Quick wins, zero budget impact.
2 Product licensed and in use? A connector without an active product behind it produces no data. Avoids broken connectors.
3 Maps to a threat scenario? Identity threats → sign-in logs. Endpoint threats → device logs. Cloud threats → activity logs. Ingestion should drive detections, not just volume.
4 Cost estimated? Use the Sentinel cost estimator before connecting high-volume sources. Prevents bill shock.
5 Data flowing? After connecting, check connector status and run TableName | take 10 to confirm. Catches silent failures early.

Step 7: Configure Watchlists

A watchlist is a reference list you upload to Sentinel (as a CSV) containing entities your organization cares about, such as VIP users, critical servers, trusted IP ranges, service accounts, terminated employees, or any custom list. Once uploaded, you can reference watchlists in analytic rules, hunting queries, and workbooks using the _GetWatchlist('watchlistname') KQL function.

📍 Portal path: Defender Portal → Microsoft Sentinel → Configuration → Watchlist → + Add new → Upload CSV → Create

Use watchlists to reduce false positives (e.g., exclude known service accounts from sign-in alerts), increase severity for high-value targets (e.g., auto-escalate incidents involving executives), or enrich investigations with business context that doesn't exist in raw logs.

Step 8: Detect & Respond

Analytic Rules: Your Detection Engine

Analytic rules are scheduled KQL queries that scan your logs for threat patterns and create incidents when conditions match. Content Hub solutions install them as templates. You activate the ones relevant to your environment. This is where Sentinel starts detecting threats.

📍 Portal path: Defender Portal → Microsoft Sentinel → Configuration → Analytics → Rule Templates → Select rule → Create rule
  • 📖 Threat Detection in Microsoft Sentinel
  • 📖 Detect Threats with Built-In Analytic Rules

Automation Rules and Playbooks: Your Response Engine

Automation rules triage incidents the moment analytic rules create them. They assign owners, set severity, add tags, run playbooks. Playbooks are Logic Apps workflows that take action: isolate devices, revoke sessions, notify Teams, create tickets.

📍 Portal path: Defender Portal → Microsoft Sentinel → Automation → Automation rules → + Create
For playbooks: Automation → Active playbooks → + Add playbook

📊 Summary Rules: Compress for Speed and Cost

Summary rules aggregate high-volume log data in the background into lean custom tables. Instead of analytic rules scanning millions of raw rows every run, they query a small pre-computed table — faster results, lower query costs, same detection quality. They work across all log tiers (Analytics, Basic, and Auxiliary). Pipeline: Summary Rule → Custom Table → Analytic Rule → Incident.

📖 Learn more: Aggregate data with summary rules

Using our two use cases as examples:

UC1 Sign-In Geo Summary

SettingValue
Destination tableSignIn_GeoSummary_CL (Analytics tier)
ScheduleEvery 1 hour
PurposePer-user location fingerprint for impossible travel
📝 View KQL: Sign-In Geo Summary 
SigninLogs
| extend
    City = tostring(LocationDetails.city),
    Country = tostring(LocationDetails.countryOrRegion),
    Lat = toreal(LocationDetails.geoCoordinates.latitude),
    Lon = toreal(LocationDetails.geoCoordinates.longitude)
| summarize
    SignInCount = count(),
    DistinctIPs = dcount(IPAddress),
    DistinctLocations = dcount(strcat(City, Country)),
    IPs = make_set(IPAddress, 20),
    Locations = make_set(strcat(City, ", ", Country), 10),
    AvgLat = avg(Lat), AvgLon = avg(Lon),
    MinTime = min(TimeGenerated), MaxTime = max(TimeGenerated)
    by UserPrincipalName, bin(TimeGenerated, 1h)
| extend MultiLocationFlag = iff(DistinctLocations > 1, true, false)

UC2 Disabled User Activity Summary

SettingValue
Destination tableDisabledUserActivity_CL (Analytics tier)
ScheduleEvery 24 hours
PurposeDaily rollup of disabled account sign-in attempts
📝 View KQL: Disabled User Activity Summary 
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == 50057
| summarize
    DailyAttempts = count(),
    UniqueIPs = dcount(IPAddress),
    UniqueApps = dcount(AppDisplayName),
    SourceIPs = make_set(IPAddress, 20),
    TargetApps = make_set(AppDisplayName, 10)
    by UserPrincipalName, bin(TimeGenerated, 1d)
| extend RiskScore = case(
    DailyAttempts >= 10 or UniqueIPs >= 3, 3,
    DailyAttempts >= 5, 2, 1)

🔍 Analytic Rules: Your Detection Engine

Analytic rules are scheduled KQL queries that scan your logs for threat patterns and create incidents when conditions match.

📖 Learn more: Detect threats with built-in analytic rules

Using our use cases as examples, here's how to tune built-in rules for your environment:

UC1 Tuned: Impossible Travel with Geo-Distance

WHY: Built-in flags unfamiliar locations. This adds distance calculation to reduce false positives.

📝 View KQL: Impossible Travel (Tuned) 
let TimeWindow = 30m;
let DistanceThresholdKm = 500;
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == 0  // Successful sign-ins only
| extend
    City = tostring(LocationDetails.city),
    Country = tostring(LocationDetails.countryOrRegion),
    Lat = toreal(LocationDetails.geoCoordinates.latitude),
    Lon = toreal(LocationDetails.geoCoordinates.longitude)
| where isnotempty(Lat) and isnotempty(Lon)
| project TimeGenerated, UserPrincipalName, IPAddress,
          City, Country, Lat, Lon, AppDisplayName
| sort by UserPrincipalName asc, TimeGenerated asc
| serialize
| extend PrevTime = prev(TimeGenerated),
         PrevUser = prev(UserPrincipalName),
         PrevIP = prev(IPAddress),
         PrevLat = prev(Lat), PrevLon = prev(Lon)
| where UserPrincipalName == PrevUser and IPAddress != PrevIP
| extend TimeDelta = TimeGenerated - PrevTime
| where TimeDelta between (1m .. TimeWindow)
// Haversine-approximated distance
| extend DistKm = 6371.0 * 2 * atan2(...)
| where DistKm > DistanceThresholdKm
| project UserPrincipalName, FirstLocation, FirstIP, FirstTime,
    SecondLocation, SecondIP, SecondTime, TimeBetweenMin, DistanceKm

UC2 Tuned: Disabled User with Risk Tiers

WHY: Built-in fires on any disabled sign-in. This adds risk tiering so SOC knows what to prioritize.

How it Works Behind the Scenes

  1. You type a natural language question in chat
  2. AI calls search_tables: finds relevant tables (SigninLogs, BehaviorAnalytics, etc.)
  3. AI writes KQL: generates a query based on the table schemas
  4. AI calls query_lake: executes the KQL against your data lake
  5. If it fails: AI self-corrects the KQL and retries
  6. AI responds: summarizes findings in plain language with the data
💡 Key point: You don't need to know KQL. The AI writes it, runs it, fixes errors, and explains results. But if you DO know KQL, you can ask it to show the query it generated so you can learn and refine.

When the built-in graphs above don't cover your scenario, build custom security knowledge graphs from any Sentinel data. Model entities (users, IPs, devices) and their relationships, then query with GQL. Build in VS Code Sentinel notebooks (PySpark) or vibe-code with @sentinel /graph-authoring.

Using our use cases as examples:

UC1 Impossible Travel

📝 Query 1: Users with multiple distant locations 
MATCH (u:User)-[s:SignedInFrom]->(ip:IPAddress)
WHERE u.uniqueIPCount > 3
RETURN u.id AS User, u.maxRiskLevel AS Risk,
       collect(DISTINCT ip.id) AS IPs,
       collect(DISTINCT ip.location) AS Locations
ORDER BY u.uniqueIPCount DESC
LIMIT 20
📝 Query 2: Specific user's sign-in footprint 
MATCH p=(u:User)-[s:SignedInFrom]->(ip:IPAddress)
WHERE u.id = 'user@contoso.com'
RETURN *
📝 Query 3: Shared IPs (lateral movement) 
MATCH (u1:User)-[:SignedInFrom]->(ip:IPAddress)
      <-[:SignedInFrom]-(u2:User)
WHERE u1.id < u2.id AND ip.distinctUserCount >= 2
RETURN ip.id AS SharedIP, ip.location AS Location,
       collect(DISTINCT u1.id) AS Users1,
       collect(DISTINCT u2.id) AS Users2
ORDER BY ip.distinctUserCount DESC LIMIT 20
📝 Query 4: Attack chain: User → IP + Alert 
MATCH (u:User)-[:SignedInFrom]->(ip:IPAddress),
      (u)-[:TriggeredAlert]->(a:Alert)
WHERE a.AlertSeverity IN ['High', 'Medium']
RETURN u.id AS User, ip.id AS IP,
       a.displayName AS Alert, a.Tactics AS Tactics
ORDER BY a.AlertSeverity DESC LIMIT 30

UC2 Disabled User

📝 Query 5: Disabled users with activity 
MATCH (u:User)-[s:SignedInFrom]->(ip:IPAddress)
WHERE u.maxRiskLevel IS NOT NULL
RETURN u.id AS DisabledUser, u.signInCount AS Attempts,
       collect(DISTINCT ip.id) AS SourceIPs
ORDER BY u.signInCount DESC LIMIT 20
📝 Query 6: What apps did they target? 
MATCH (u:User)-[:AccessedApp]->(app:Application)
WHERE u.id = 'terminated.user@contoso.com'
RETURN u.id AS User,
       collect(DISTINCT app.displayName) AS TargetApps
📝 Query 7: Full blast radius 
MATCH p=(u:User)-[r]->(target)
WHERE u.id = 'terminated.user@contoso.com'
RETURN *

💡 This one query visualizes everything the disabled account touched. IPs, apps, devices, alerts.

📝 Query 8: Peer deviation 
MATCH (u:User)-[:PeerOf]->(peer:User),
      (u)-[:AccessedApp]->(app:Application)
WHERE NOT EXISTS {
    MATCH (peer)-[:AccessedApp]->(app)
}
AND u.id = 'terminated.user@contoso.com'
RETURN u.id AS DisabledUser, peer.id AS Peer,
       app.displayName AS UniqueApp LIMIT 20
